## この研究のゴール（毎回、着手する問いをここに照らすこと）

**多峰度の高い問題（大域最適が多い問題）で、既存手法より多くの大域最適を見つける。**

分野の系統的レビュー（[Algorithms 17(10):448, 2024](https://doi.org/10.3390/a17100448)）が
未解決課題として「次元と多峰度が高いときのスケーラビリティ」を挙げ、今後の方向として
"space and time-scalable methods" を名指ししている。実測でも headroom はここに集中する:
K=36 の N07 では最良手法が PR 0.97 に届くのに、K=216 の N09 では 0.49、他手法はほぼ 0.25 未満。

- **主指標**: CEC2013 niching の peak ratio（精度 ε = 1e-1 〜 1e-5）。**特に K の大きい関数**
  （N06 K=18 / N07 K=36 / N08 K=81 / N09 K=216）。
  **ただし手法の判定は ε ≤ 1e-3 で行う**（その28）。1e-1 は報告規則の質を測っており、
  報告規則を揃えると 7 手法中 7 手法が N07 で 1.00 に張り付いて識別力を失う。
  1e-1 / 1e-2 は参考値として併記してよいが、順位の根拠にしない。
- **この研究における「多様性」の定義**: 精度 ε 以内で発見された相異なる大域最適の数。
  分野の標準定義を採り、自作の定義は使わない。
- **比較対象**: NMMSO / NCDE / Crowding-DE / r3pso / NM-Restart / MC-ESO。現状の首位は NMMSO。
- **手法は自由**。MC-ESO を改善する必要はない。比較対象の 1 つとして残すだけ。
  ただし MC-ESO 自体を壊さない（BBOB-24 dim2 の SR@1e-10 93.5% は既存資産として保つ）。

**問いを選ぶときの条件**: その問いが片付くと、K の大きい関数の peak ratio が上がるか、
上がらない方向を確実に潰せるか。どちらでもない問いは、面白くても後回しにする。

**占有されている領域**（実装前に必ず確認したこと）:

- **報告規則を独立した設計対象にすること**は済み。[Peak Identification in Evolutionary
  Multimodal Optimization](https://pmc.ncbi.nlm.nih.gov/articles/PMC11505590/) が探索と選別を
  2 相に分け、niche 半径不要の HVPI と冗長解を罰する F 値を提案している。
- **報告効率を測ること**も済み。GECCO competition の Dynamic F1（報告解のうち相異なる
  大域最適だった割合の、評価回数に沿った積分）。
- **持続性による盆地分解**は [arXiv 2605.18351](https://arxiv.org/pdf/2605.18351) が占有。

**分かっている手がかり**（過去の測定から。**数値・表・機序の全文は
[acceptance_topology.md の「多峰テーマ（peak ratio）の確定事項」](acceptance_topology.md#多峰テーマpeak-ratioの確定事項)**
にある。ここは見出しだけ）:

- **受理規則が深さと広さを同時に決めている。** 親比較なら深さ、最近傍置換なら広さ。
  1 つのつまみでは両立しない（MC-ESO で SR@1e-10 100% → 0%、DE / PSO でも同傾向）。
- **効くのは返す個数ではなく、上位が互いに別物であること。**
- **MC-ESO はどちらの地形でも「盆地は見つけるが掘り切らない」**（その20 で統一された）。
  Shubert は PR@1e-1 0.80 → PR@1e-5 0.15。Vincent は報告規則のせいで見えにくかっただけで、
  履歴を見れば N09 の 216 個すべてに 1e-1 まで近づいており、1e-3 まで降りるのは約 28 個。
  **かつて「Vincent はそもそも見つけない」と書いていたのは誤り**（報告集合しか見ていなかった）。
- **hunt 単位で見ると `reported ≈ min(distinct hunts, deep hunts)`**（その21）。
  **Vincent は distinct（被覆）側、Shubert は deep（深さ）側が binding。**
  Vincent には局所最適が存在しないので、盆地に入りさえすれば必ず降り切る。
- **PR は evals/K でも K でも決まらない**（その17）。分けているのは
  **予算を新しい最適解に変換し続けられるか**。r3pso は完全に飽和、MC-ESO は高 K でだけ飽和、
  NMMSO だけが高 K でも変換し続ける。
- **報告枠は制約になっていない**（その19・その20）。採点上限 max(100, 2K) に対し
  MC-ESO は 88 点しか報告していないが、履歴から選び直しても利得は **eps=1e-1 に集中**する。
  1e-3 以下では実質同等なので、**報告規則側の残り代は浅い**。
- **報告規則の路線は 7 手法で測って閉じた**（その28）。選び直しを全手法に与えると
  利得は**全手法で eps=1e-1 に集中**し（N07 は 7/7 手法が PR@1e-1 = 1.00 に張り付く）、
  **eps ≤ 1e-3 では上位 2 位が全 5 関数で一切動かない**。
  **NMMSO が最も利得を受けない手法**なので、この路線で首位との差は埋まらない。
  → **運用規則: PR@1e-1 で手法を比較しない。判定は 1e-3 以下で行う**（下記）。
- **再起動の被覆を決めているのは描画ではなく選抜**（その22）。盆地切替は 20 スロット全部を
  独立に反発描画するので描画は全 36 解を覆うが、μ+λ 貪欲の best-of-20 が系統的に広い盆地の
  点を選ぶため着地は 11-15 解に留まる。**描画規則や σ_init（箱に対する固定比）を変えても
  この偏りは動かない。**
- **`sigma_only` の利得は hunt 数ではない**（その25）。予算を 40% 増やして hunt 数を
  追い越させた base（51.5 対 49.1）でも N07 の PR@1e-3 は届かず 15 seed 全敗。
  ただし **σ と予算は別の精度水準に効く**（Shubert の粗い水準は予算律速で σ は動かさない）。
  **解放規則（`hunt_no_improve_mult` / `exhausted_sigma_tol`）では base の hunt 数は上がらない。**
- **ただし「σ を局所盆地間隔に合わせる」は別のつまみで、これは効く**（その23）。
  再起動後の σ を `0.1 × d_local`（観測済み盆地重心の最近傍距離、追加評価ゼロ）にすると
  N07 の PR は全 eps で 0.22 → 0.34（15/15 seed）、さらに 20 本の描画を 1 本に commit すると
  0.44。着地した相異なる最適解は 11/36 → 26/36。**箱に対する比と局所盆地間隔に対する比を
  混同しないこと** — その22 が振ったのは前者、効いたのは後者。
- **しかしその利得は 2D 限定で、路線ごと畳んだ**（その26・その27）。**N08-Shubert3D では符号が反転し**
  （PR@1e-1 が base 0.34 に対し 0.20、5 seed 全敗）、**比を 0.1 / 0.25 / 0.5 と振っても
  内点に最適は無い**（全カラムが単調に base へ戻る）。**痛みが消える 0.5 は効果も消えている**
  （深精度の利得が 5 seed 全部で base と同値）。3D では深さの利得が**有償**になる
  ＝ **次元が上がると深さと広さが再結合する**。詳細は
  [acceptance_topology.md の該当節](acceptance_topology.md#局所盆地間隔スケーリングは-2d-限定で確定--3d-では比が単調なトレードオフダイヤルになるその26その27-analysishmn08_csv)。
  **BBOB-24 dim2 はこの路線に対する識別力を持たない** — 盆地が 3 個未満だと base の経路に
  落ちるので、全 24 関数で MC-ESO とビット一致する（＝安全の証拠ではなく未発火の証拠）。
- **N08-Shubert3D の 1e-5 は判定に使えない** — base が 5 seed すべてちょうど 1 解（PR = 0.01）。
  **3D の判定は 1e-1 / 1e-3 で行う。**
- **規則側の梃子は全部閉じた**（その29）。**σ のスケールと受理規則という構造的に無関係な 2 つの介入が、
  同じ深さ↔広さの線の上を動く**（どちらも distinct を増やし `blocked` を 4-5 倍にし landed を減らす、
  同一の署名）。位相分け（枯渇まで親比較、枯渇後だけ最近傍置換）も**深さを分離しない** —
  最初の枯渇までに稼げるのは最初の 1 盆地の深さだけで、**必要な深さは境界の守られない側に全部ある**。
  **1 本の hunt に落ちる評価回数を変えない限り線から出られない**ので、残るのは配分側。
- **ただし「規則側は全部閉じた」は不完全だった**（その30）。**Shubert の深さを止めていたのは
  `hunt_level_tol`** で、`has_exhausted` 以降の hunt は `basin_best <= hunt_level_tol * f_init_scale`
  で解放される（`mceso.py:919-928`）。既定 1e-6 では**解放水準が eps=1e-3 と eps=1e-5 の間**に落ちるので、
  捨てた盆地の 9 割が (1e-5, 1e-3] に溜まる。1e-8 にすると **N06 の PR@1e-5 が 0.17 → 0.76**
  （15 seed 全勝、A12 = 1.00、粗い水準の代償は有意でない）＝ **本テーマ最大の利得**。
  **N07-Vincent2D では no-op**（被覆律速なので深さの梃子は効かない、その21 の二分法どおり）。
  **その29 の「1 本の hunt に落ちる評価回数を変えない限り線から出られない」は正しく、
  `hunt_level_tol` がまさにその評価回数を決める規則だった。**
  **採用可否は未決（安全性が未測定、下記の gate の盲点のため）。**
- **`blocked` が大きいことは「回収可能な在庫がある」ことを意味しない**（その30）。
  報告集合を成分に分けると `blocked` は**全部「最後の hunt の生きている population」**で、
  置き去りの盆地ではなく**予算が尽きた時点の現在地**だった。入って捨てて戻らなかった真の在庫は
  **N06 で 0.3、N07 で 0.0**（K = 18 / 36）。**成分に分けるまで在庫の有無は判定できない。**
- **BBOB-24 dim2 / 5000 評価の gate は「枯渇後だけを触る介入」に対して構造的に盲目**（その29）。
  `phased` は**全生成のおよそ半分で発火している**のに全 24 関数で tie_count = 20。理由も測った:
  **24 run のうち最初の枯渇より後に best_f が改善した run は 0 個**。
  **この gate を通ったことは安全の証拠にならない**（その26 の「発火していない」より強い）。

## 1 サイクルの手順

**このループは 1 時間ごとに走る。前の回がまだ走っている可能性があるので、手順 0 と 1 を飛ばすと二重着手になる。**

0. **ブランチを合わせる** — `git fetch origin && git checkout research-loop && git pull --rebase origin research-loop`（無ければ main から作る）。**成果は全部この 1 本に積む。** 実行ごとにブランチを切らない。切ると前回の続きから進めなくなり、統合されない成果物が散る。main には触らない（人がマージする）。
1. **問いを 1 つ claim する** — 「未解決の問い」の上から、まだ claim されていないものを 1 つ選び、その行に `(claimed YYYY-MM-DD HH:MM UTC)` と書いて**即コミット・push する**。これで他の回は別の問いを選ぶ。**2 時間以上前の claim は放棄されたものとみなして奪ってよい**（奪ったら時刻を書き換える）。
2. **統合の回かを判定する** — 「作業ログ」の件数が **8 件を超えていたら、新しい実験をせずに統合作業をする**。すなわち: ログの結論を `acceptance_topology.md` の該当節に集約し、決着した問いを「未解決の問い」から消し、ログを直近 3 件＋要約に畳む。積み上がらない一番の原因は記録が増えるだけで整理されないことなので、これは実験より優先する。
3. **先行研究を潰す** — 実装の前に、隣接分野の語彙で検索する（下記「先行調査の鉄則」）。既にあるなら問いを畳んで記録し、次の問いへ。
4. **設計する** — 何を測れば白黒つくか、どういう結果なら仮説が否定されるかを先に書く。撤退条件のない実験はしない。
5. **実装して回す** — 小さく回して配線を確認してから本測定。既存スクリプトで足りるなら新規作成しない。**1 回の計算は 40 分以内**に収める。収まらないなら関数か seed を削り、削ったと書く。
6. **分析する** — 対応のある検定と効果量、seed 方向一致率。平均だけで結論を出さない。
7. **記録してコミットする** — 「作業ログ」に追記し、claim を外して結果を書く（決着したら問いを消す、続きがあれば次の問いとして書く）。**否定的結果も機序つきで残す**。`research-loop` に push する。push が競合したら `git pull --rebase` して再試行。

**1 回で全部やろうとしない。** claim した問いが 40 分で終わらないと分かったら、そこまでの結果と「次はここから」をログに書いて終える。中途半端な状態を残すより、次の回が続きから入れる形にすることが優先。

## 守る規則（これまでの失敗から）

**先行調査の鉄則** — 新しい定式化を思いついたら、**実装より先に 4 分野以上の語彙で検索する**。この研究では 2 回、提案の中核が先行研究と一致して撤退した。

- 進化計算（niching / QD / EDO）だけでなく、ロバスト最適化（K-adaptability, ROMS）、設計工学（solution space engineering, set-based design）、計算化学（disconnectivity graph, barrier tree, NEB）、統計（cluster tree）、TDA（merge tree, persistence）、能動学習（level set estimation）の用語で引く。
- 「barrier tree は調べたが disconnectivity graph では引かなかった」で 1 日を失った。**同じ概念の別名を列挙してから検索する。**

**測定の鉄則**

- **単一 seed で結論を出さない。** 1 seed では NM-Restart が最良と出た関数で、3 seed では最下位になった。
- **集計から落ちた対象を必ず報告する。** 比が定義できない関数を黙って除くと順位が変わる（実際に変わった）。
- **定義を変えたら結果がどう動くかを測る。** τ・重複除去半径・行動記述子・シナリオモデルはいずれも答えを桁で動かした。定義依存性は欠陥ではなく報告事項。
- **推定器の誤りの向きを述べる。** 線分による連結判定は繋がりを見落とす側にしか誤らない、など。
- **後処理の利得は 1 手法で測らない。** 報告規則のように**手法非依存に当てられる**ものは、
  1 手法で測ると必ず「効く」ように見える。その20 は MC-ESO 単独で PR@1e-1 を 0.25 → 1.00 に
  上げたが、その28 で 7 手法に与えたら**全員が上がり順位は 1e-3 以下で不動**だった。
  **他手法にも与えられる介入は、他手法にも与えてから読む。**
- **同一 run を 2 通りに採点できるなら、そうする。** その28 は 1 セットの run を
  2 つの報告規則で採点したので、ペアリングが厳密で追加評価はゼロだった。
  比較のために run を 2 回回すと、seed 差が交絡として入る。

**リポジトリに何を残すか**

差分の 99.7% が機械の吐いた生 CSV になり、レビューできない状態になった（2026-09-03 に整理）。

- **行単位の生 CSV は `.csv.gz` で置く。** 生のまま置いてよいのは数百行までの集計結果。
- **数値は必ず docs に書き出す。** CSV は再解析のための控えであって、結論の置き場ではない。
  docs を読めば結論が分かる状態にしてから commit する。
- **路線が畳まれたら、その生データも消す。** 結論は `acceptance_topology.md` に残っており、
  git の履歴からも取り出せる。畳んだ路線の生データを抱えたままにしない。
- 1 回のサイクルで `analysis/` に足す行数は、gzip 前で 10 万行を目安に収める。
  超えるなら集計してから置く。

**main へのマージ**

`research-loop` は 1 日 1 回を目安に `main` へマージする（マージはユーザーが決める）。
溜めると差分が読めなくなり、読めない差分はレビューされない。

**MC-ESO を壊さない**

- `SR@1e-10` を下げる構成は採用しない（多解の改善でも例外なし）。
- 既定値を変えたら **BBOB-24 dim2 / n=20 で SR@1e-10 93.5% / evals_succ_mean 798** と一致することを確認してからコミットする。
- 診断用の変種は本体を書き換えず別ファイルに置く（例: `mceso_crowding.py`）。

## 未解決の問い（上から着手する）

claim 中のものは `(claimed ...)` が付く。2 時間以上前の claim は奪ってよい。
